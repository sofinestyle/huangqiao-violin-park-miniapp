# 备份与恢复

结论：保留用户“数据库每3天、图片每周增量、30天清理”的要求作为最低设计输入；建议正式预约数据提高到每日自动备份并按实际PG能力启用日志恢复。调整属于建议，未配置任务、未修改现有周期。

## 1. 当前与云端差异

server/backup.mjs的VACUUM INTO + media文件清单/SHA适用于SQLite；restore只写新目录并删除旧Session，避免恢复后重用旧登录态。本轮只读代码，没有执行备份恢复。源码/文档搜索未发现上述周期的调度实现，不应写成“已每天/每周自动备份”。

CloudBase PG [FAQ](https://docs.cloudbase.net/en/database/postgresql/faq)说明备份依托腾讯云PostgreSQL并有自动/手动方式。腾讯云[PG备份设置](https://cloud.tencent.com/document/product/409/68388)给出可配置计划与保留，但CloudBase共享/独享实例具体入口、权限、保留期、PITR及下载能力必须在目标环境确认；不能把文档数据库回档、MySQL备份或套餐“14天回档”直接宣称为PG保证。

## 2. 周期设计与恢复点

| 对象 | 用户要求的落地建议 | 改善建议及理由 |
| --- | --- | --- |
| PG业务库 | 每72小时生成一次可恢复的应用Schema备份，任务记录开始/结束/校验/版本；由持久调度器执行 | 优先每日平台自动备份，若支持日志/PITR则开启并演练，降低丢失预约风险；每3天逻辑导出作为独立副本 |
| 图片 | 每周按不可变object key+SHA清单做增量备份 | 增量须有完整基线；正式上传频繁则每日复制新增对象，避免DB恢复后缺最近一周图片 |
| 教学视频 | 同样进入对象备份清单，不只备份图片 | 文件大要核算备份与恢复流量；不能省略导致教学空记录 |
| 30天清理 | 清理过期备份集、临时产物和无依赖历史备份版本 | 不是删除30天前的商品、咨询、审计或仍引用媒体；保留链依赖/最近可用全量，先确认新备份可恢复 |
| 重大变更前 | PG Schema/配置+对象清单独立快照 | 保留Migration/镜像/静态构建版本及恢复说明，失败可定位兼容版本 |

按最低周期，DB灾难可能损失接近3天新增记录，对象可能损失近7天；这是风险推导而非承诺RPO。跨DB+对象的有效恢复点取二者共同完整状态，不能拿“DB每天”宣称整个系统RPO一天。RTO须实际测量数据量和带宽，当前无可靠时长。

## 3. 联合备份结构

建议备份manifest至少含：环境、时间、PG主版本/应用Migration版本及校验和、Server/Admin/小程序兼容版本、备份文件哈希、应用表范围、media ID→bucket/key/对象版本/SHA/size，以及校验结果。备份应加密、仅恢复负责人可读，目标与生产运行身份分离。

pg_dump适合应用Schema逻辑备份；不复制CloudBase托管的auth/storage系统表覆盖新环境，不要求业务账号成为超级管理员。Restore通过平台允许的DDL路径重建应用Schema，再按可用DML权限导入；直接pg_restore的建表权限受平台限制，须在staging验证。[PostgreSQL逻辑备份](https://www.postgresql.org/docs/current/backup-dump.html)。

PG逻辑快照与对象复制非一个事务：采用不可变对象key、先完成对象上传再提交metadata、不自动删除引用对象；基于DB快照中的media清单复制对应版本。若任何对象缺失或SHA不符，该备份不得标记完整。对象版本化/跨故障域复制须核对PG Storage实际管理能力；没有原生版本化时，可用独立备份桶按清单复制，不宣称已开启COS版本控制。平台storage元数据需要通过正式对象上传/恢复API重建关联，不仅复制底层COS字节。

定时任务必须位于持久调度器/专用任务，不用可缩容到0的Node实例setInterval。任务失败告警、有限重试、幂等目标、保留最近成功清单；未获资源批准前不创建云函数、Cron或备份桶。

## 4. 灾难恢复步骤（待演练）

1. 负责人确认事故范围，停止写入/隔离入口，保留故障日志；选择同时覆盖DB与对象的完整恢复点，告知可能丢失窗口。
2. 在新隔离目标创建匹配PG主版本与平台系统环境，验证迁移权限，恢复应用Schema/数据/索引/序列和必要配置，不覆盖原环境。
3. 恢复对象并校验全部media引用的大小/SHA/可读取性；同步平台Storage元数据，不把桶改成public绕过错误。
4. 校验13表数量/PK/FK/唯一/JSON、SKU ID/Code/组合、预约已占容量、咨询历史快照及audit；保留幂等记录避免灾后重试创建重复业务。失效恢复出的Session，轮换泄露风险凭据。
5. 验证Admin角色、微信本人记录、发布/下架、SKU公开图片/历史后台图、Range；对比manifest版本与应用兼容性。
6. 人工批准切换入口，观察错误率与业务结果；旧环境只读保留到批准清理窗口，不立即销毁。

建议正式上线前一次完整演练，之后定期抽样并在核心Migration后复演；频率/恢复负责人和预算由项目负责人落实。本轮未创建备份任务、未恢复任何数据库、未宣称达到RPO/RTO。
