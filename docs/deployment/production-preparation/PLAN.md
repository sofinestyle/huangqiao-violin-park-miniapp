## 3. 必须先解决的代码与测试入口边界

以下为待实施建议S，不是本轮已批准执行的代码改动。

1. **正式构建及运行身份。** 在environment-settings.ts、config.ts、build-mini.mjs及必要测试中准备显式Production候选；验证真实API、AppID、资源身份后才启用。release不再被当前保护阻断，同时继续拒绝空目标、localhost和未知环境。不能仅添加release白名单而保留trial固定测试身份。
2. **候选体验入口。** 经批准的正式候选体验版与后续审核/发布使用同一已转正API；普通开发构建、页面参数、本地缓存不得切入正式写入环境。访客令牌按production独立存储；不能复用旧staging缓存冒充正式身份。
3. **旧测试入口。** 原Staging构建和已分发体验版连接的是同一个资源；转正后将能触及正式数据。需盘点、撤销或替换旧体验访问，停用旧测试构建目标和自动化写入；已安装旧客户端不能仅靠改菜单视为失效，必要时经批准增加服务端可验证的版本/访问限制。具体限制方案待检查现有身份协议，不能承诺仅改客户端标签即可阻断旧写入。
4. **服务端转正。** 按批准窗口设置正式运行身份，关闭测试认证和Seed；核对EnvId、服务、数据库、媒体资源与部署制品绑定。保留现有Cookie的HttpOnly、Secure、SameSite、同源路由、唯一ADMIN_ORIGIN和CSRF检查，不放宽CORS或Origin。
5. **测试隔离。** Development及未来测试环境不得共享正式业务库写入凭据。安全证明改为“转正资源与本地/未来测试资源隔离”，不能再要求正式连接与转正前Staging连接不同；二者是负责人明确选择复用的同一资源。

旧webapps及网关后台入口当前跳转admin.yorray.com；转正后这些入口同样进入正式后台，不再称为独立Staging后台。需明确其正式兼容入口或退役策略，但不降低登录及CSRF保护。自动化仍保持暂停，不因转正方案恢复。

## 4. 现有资料直接沿用与isTest兼容检查

业务内容不迁移、不重新录入。上线前只需针对当前真实库做只读清单核对：已发布/草稿、isTest标记、媒体关联、旧/assets与localhost路径、测试账号和测试运营记录。负责人已确认资料的业务用途，不需要因本方案再次逐条批准相同内容。

本轮源码核对发现：

- server/pg/foundation.mjs的saveContent在production拒绝isTest=true；非production保存时强制测试标记。
- admin/src/Content.jsx的createDraft固定isTest=true。现有内容若保留此标记，编辑提交也可能被正式服务拒绝。因此需要环境感知的新建/保存适配，并核实已批准内容的标记处理。
- server/service.mjs公开列表以state=published筛选，Foundation详情也按发布状态检查，当前读取未以isTest过滤。不能声称只改APP_ENV就会让全部旧资料消失；已确认风险主要是正式维护保存兼容性。

若实际库仍有测试标记，后续可在明确授权、备份和Dry-run清单下仅对已批准业务内容做元数据调整；这不是搬库或业务数据迁移，但仍是数据写入，本轮不执行。不得关闭生产保护来绕过，也不得把账号、会话、预约、咨询、审计等全部批量“转正”或删除。

已有账号和权限保留，不运行空库管理员初始化，不覆盖密码。会话失效、权限收紧、测试记录清理或标记处理如有需要，应分别列出对象与影响后实施；登录本身会产生正常会话/审计，不能称为严格零写入。业务资料通过人工核查，不等于这些技术元数据或所有历史运营记录已经核实。

**备份：** 转正前需要当前有效备份与媒体关联校验；恢复能力在另一个隔离目标演练，不能对准备转正的现有库执行restore。现有恢复代码要求所有非系统表为空并将媒体恢复交给本地目录，CloudBase平台表及私有媒体适配仍须验证。原每3天数据库、每周图片、保留30天的政策输入保留；提高频率、视频覆盖、独立故障域及恢复目标作为待落实运维建议，不冒充已执行。
