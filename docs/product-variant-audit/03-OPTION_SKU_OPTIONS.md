# 方案A与方案B：结构、维护与边界

基准及当前事实见 [01](01-CURRENT_MODEL.md)。本篇全部目标字段、交互、数量上限、编码策略均为**候选建议，未批准、未实施**。独立结论：推荐B，但不建议当前直接建设完整商品交易或四表属性平台。

## 1. 两条路线

| 判断 | A：保留specs JSON，仅改Admin | B：Product→Options→SKU |
|---|---|---|
| 可行性 | 可做紧凑表格、折叠、批量价/图片，提高录入效率 | 可在SQLite及现有服务内渐进实现；无需换框架 |
| 尺寸×颜色 | 能保存10个组合名称，但维度不被数据库理解 | 维度和值有稳定ID，组合对应稳定SKU |
| 自动生成组合 | UI可以临时生成并拼接name；不能说“技术上完全不能生成” | 可持久保留维度、值及组合身份，增删按差分处理 |
| 是否人工建10行 | 可用临时生成器减少手工，但再次编辑时只能读取自由文本行；不能可靠逆解析 | 不必重复建立；确认维度后生成矩阵，人工只填差异 |
| 批量改价/图库 | 可行，仍整体保存specs；增加相应UI及回归即可 | 可行，稳定ID定位；批量仍需权限、版本与原子事务 |
| 历史与改名 | 名称仍是咨询识别条件，重名/改名风险不消失 | ID独立于名称/编码，历史快照保留 |
| ERP/独立站 | 需要日后人工映射和重新迁移；拼接名称不能作为可靠通用接口 | 更适于映射产品编码、SKU编码、Option、参考价、图片、状态 |
| 主要优点 | 边界小、无数据迁移、短期低风险 | 从身份和组合语义解决问题，降低日后映射成本 |
| 主要缺点 | 自由文本技术债保留；临时矩阵不能可靠重建维度 | 数据与多客户端兼容成本明显更高，需要DCR与迁移演练 |

A若只是折叠表单，开发成本低；加入临时组合生成/批量矩阵会升至Medium，且容易形成“看起来结构化、保存后仍是字符串”的误导。单纯SKU改名也不能让系统自动具备ERP接口。

## 2. 四个场景逐项评估

| 场景 | 现有模型维护和重复 | 查询/游客展示 | 对接与B收益 |
|---|---|---|---|
| A：5尺寸×2颜色=10 | 10个纵向规格块，名称重复尺寸/颜色；两套图须分别关联相应行，无需上传10次 | 现有横向名称标签可用但没有两维筛选；服务端不能按颜色/尺寸结构查询 | A需要文本映射；B保留10个SKU和两维属性、稳定组合差分 |
| B：5×2×2套装=20 | 20行参数/价/图差异容易漏填，最长说明受总JSON长度限制 | 展示20个标签可运行但选择负担高；字符串搜索易歧义 | B用三维选择和20条矩阵；缺货概念仍不引入，只管理启停 |
| C：T恤4尺码×3色=12 | 文创同一product模型，12行同样重复；不能把S/M名称视为统一属性字典 | 现有详情共用可显示12标签，列表仍仅产品级 | B允许每产品维度名称不同；不得强制所有产品都叫“尺寸” |
| D：只有4/4 | 当前1行成本低，无需组合生成 | 一个标签和默认图足够；暂无结构查询需求 | B简单模式保留单SKU及原4/4含义，不能要求用户维护矩阵 |

10、20、12均低于当前50条规格上限，因此不能把“当前无法保存这些数量”作为升级理由。问题是身份、维度、维护及长期关联，而非当前SQLite容量不足；本轮没有性能测试或真实10/20条操作计时。

## 3. SQLite存储方案比较

| 候选 | 优势 | 代价/适用性 |
|---|---|---|
| 四表：product_options、product_option_values、product_skus、sku_option_values | FK关系清楚，跨产品属性查询、值引用和组合映射容易索引 | 更多表、连接、迁移和一致性约束；单靠四表仍需处理组合唯一性；当前28个开发产品尚无跨产品属性查询需求，立即全部采用偏重 |
| 全JSON：产品options与skus数组 | 接近现有整体保存、一次读取；小矩阵简单 | 可以给JSON项稳定ID，不能误称JSON完全不支持身份；但跨产品SKU编码唯一性、独立SKU查找/引用需额外扫描、触发器或旁表，整体替换仍易丢失旧项 |
| **建议B的折中：产品Options JSON + 独立product_skus表** | 维度少、随产品维护；SKU可PK/唯一编码/产品索引查询；比四表少，保留扩展通道 | Option值引用由Service校验，数据库FK不能直接指向JSON数组项；必须所有写入走统一事务验证 |

SQLite支持JSON读取/遍历，但把数组存进JSON不自动获得元素级关系约束，这是本项目结构选择的依据之一。[SQLite JSON官方文档](https://www.sqlite.org/json1.html)。独立SKU表的产品FK须正确启用、父键须满足主键/唯一性要求；本项目已有外键启用机制，应沿用并测试。[SQLite外键官方文档](https://www.sqlite.org/foreignkeys.html)。

建议现在不建跨产品通用属性库。未来若明确需要按颜色跨产品筛选、共享属性字典或外部系统批量同步，可保持Option/Value ID不变再规范化；不提前声称一定需要四表，也不把全JSON实现说成不可行。

## 4. 推荐候选字段与约束

| 实体 | 候选字段 | 说明 |
|---|---|---|
| 原content产品 | 原产品字段；modelVersion、variantMode；options JSON | mode候选simple/options/legacy；共性信息及发布状态保持产品级 |
| options[] | id、name、sort_order、values[] | ID独立于“颜色”等标签；值拥有id、label、sort_order及退役标记；产品局部定义 |
| product_skus | id、product_id、sku_code、option_values、combination_key、reference_price、images、enabled、sort_order | id稳定；product_id引用content.id，Service另校验kind=product；option_values为OptionID→ValueID；images延用现有URL数组 |
| 兼容数据 | legacy_name、legacy_description、legacy_payload、legacy_source_key | 保存原始name/description及所有未知字段；溯源键避免重复迁移；实际归档位置与保留期待DCR |

建议约束：SKU主键唯一；非空sku_code在本系统全局唯一（大小写、空白、编码可修改性需确认）；structured组合按排序后的OptionID/ValueID建立唯一规范键，约束 `(product_id,combination_key)`。显示顺序不参与身份；label改名不改变组合键。legacy未映射项使用空组合键并靠SKU ID区分，不能把全部旧项当成同一个“空组合”。simple模式约束一个Default SKU。

数据库新增product_id查询索引及组合/编码唯一约束是实施候选，并非本轮Migration。选值存在性、每维恰选一值、值归属、生成数量、enabled语义由服务端统一校验；不只信任前端矩阵。整产品content.version可继续作为原子保存版本，不必立刻增加每SKU独立并发协议。保存options及SKUs应在同一事务完成。

## 5. SKU Code与参考价

已有Product Code。建议新增独立SKU Code用于员工及外部对照，稳定SKU ID永远不依赖编码字符串。候选“自动生成并允许受控人工修改”比让员工手写全部编码更实用；一旦外部引用应保护旧编码映射并审计。现阶段**不冻结** L201-44-BR之类格式、前缀、序列、大小写或是否允许永久改码；legacy可先无code，正式对接前完成映射和唯一检查。自动生成策略仍需冲突处理，不能依赖产品编码当前天然唯一。

参考价继续是展示/咨询辅助。建议SKU空覆盖值时使用产品默认参考价；0必须显示为0而非回退。产品inquiry时是否隐藏所有SKU价须业务确认，因现页面并非如此。币种、精度与“参考价”文案仍需DCR：候选保持现有数值精度和原始值，不在迁移中四舍五入或强制转分；若未来决定整数分，先检查超过两位小数及精度损失，单独批准转换。任何SKU价都不自动成为ERP销售价或订单结算价。

## 6. 生成、差分与删除

1. 先计算笛卡尔积及数量，显示预览，不立即覆写。按稳定值ID生成combination_key，与已有SKU求交集/新增/退出。
2. 交集SKU保留id、code、覆盖价格、图片、启停及人工排序。新增SKU赋新ID、使用默认价/图规则；新增项附后，排序可独立调整。不得每次重新编号并重建全部SKU。
3. 删除“棕色”时，先列出5个退出组合及关联摘要；默认**停用这5个SKU、退役该值，保留其身份与历史数据**。公共新选择不可选，既有咨询快照仍可回看。不把停用等同删除文件。
4. 同一值恢复可恢复原ID及SKU；同名字新建值不自动认作历史值。删除整维可能多对一合并，新增维可能一对多拆分，不能自动决定旧ID归谁；需差异预览、人工确认并保留旧SKU。
5. 父产品未发布时SKU enabled不能使其公开；产品发布也不自动重新启用被停用SKU。全SKU停用时应给咨询无可选规格的明确说明，具体是否仍允许产品级咨询待DCR。

## 7. 图片与批量维护MVP

建议先延续两级：SKU非空图库优先，否则Product Gallery；不复制文件。MVP提供按选中SKU批量设参考价、启用、停用、清空SKU图以继承产品图、共享同一组图片URL，提交前展示影响条数。覆盖已有值时应明确覆盖范围，保留未选中SKU差异。

10个SKU仅2种颜色图片：当前可只上传两组文件，但通常需逐行配置10次引用；新矩阵按颜色选中5行分别批量关联两次即可。JSON里重复URL只是引用，并非10份文件存储。后续若颜色共享图库成为常态，再评估“SKU显式覆盖 > 颜色值图库 > 产品图库”的三级继承；多维同时配置图库的优先级须先定义，MVP不引入含糊的自动合并。

后续项：颜色值级图库、跨产品批量编辑、外部渠道同步、复杂条件组合、定价公式；都不属于本次审计授权，也不建议混入首个SKU实施范围。

## 8. 单规格与数量保护

建议底层统一SKU、UI分简单模式与多规格模式。新简单产品自动持有一个Default SKU，表单只维护产品及必要差异，不强迫展示“Default”标签。已有单规格4/4先保留原名称/说明/图/价；有明确尺寸含义时可经人工映射为一个尺寸值，不丢失4/4事实。旧零规格产品需要兼容投影维持旧页面不出现多余规格栏。

候选上限：最多3维，每维最多50值，实际当前组合乘积最多50；任一维或总乘积超过限制即阻止生成，20以上先提醒审阅。每维50是为单维产品保留现有50条上限，**不是允许50×50×50**。上限按当前可维护矩阵计算；退役历史SKU不能因上限被删除，历史保留/列表分页需另定。

依据：现有50条限制、当前最多5条、已提出最大20组合场景和后台录入效率；并非性能测算结论。现有50,000字符JSON与请求体上限、图片数量也须纳入实施容量验证；即使移出SKU表也不能放开无限请求。所有上限均是S级建议，等待业务确认。

## 9. 游客与外部系统方向

游客详情可逐维选择尺寸/颜色/套装，解析唯一enabled SKU，更新图片、参考价及咨询携带的skuId；无效组合清楚禁选并保留可读原因。列表继续产品级，避免因模型升级重写全站；不新增购物车、库存、购买或支付。

未来Violin ERP Lite、YorRay独立站及其他渠道通常需要明确产品与可区分变体的映射。一个公开实例是Shopify ProductVariant具有SKU、selectedOptions和价格等字段，说明结构化变体更便于映射，但不代表本项目采用Shopify。[官方ProductVariant文档](https://shopify.dev/docs/api/admin-graphql/latest/objects/ProductVariant)。

本次未访问ERP或独立站代码/API，不能断言它们当前字段、编码唯一规则或可直接互通。未来必须确认主数据归属、同步方向、外部ID映射、币种/价目表、状态语义和冲突规则；本模型只保留适配基础，参考价不替代外部成交价，enabled不等于库存可售。
