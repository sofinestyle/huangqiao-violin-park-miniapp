# 最终推荐与人工决策入口

**RECOMMEND B：先确认结构化规格及稳定SKU身份，再实施紧凑矩阵；优先候选为产品局部Options JSON + 独立SKU表。** 本报告是审计和建议，尚未冻结最终Schema、API、编码或操作规则。

基准：`c351092da1cc99f49a91a67f4ad62124dcf5e716`，main。正式审计范围仅本目录6份Markdown与证据JSON；没有修改业务、UI、测试、数据库、Migration或其它治理文件。

## 1. 为什么选B，而不是顺从“规格太长就换模型”

当前50条自由文本规格完全可以保存10/20/12种组合，当前库也没有证据证明规格参数大规模重复。因此如果只有5个固定尺寸、没有跨系统或维度需求，A的紧凑表格更经济，不应以页面长度单独证明B必要。

本次选择B的决定性因素是：已明确要求评估尺寸×颜色×套装；现规格没有稳定ID，咨询以名称匹配，无法可靠保留组合变更身份；未来ERP/独立站映射需要独立编码和选项语义。A能批量生成文字和改价，却仍不能持久记录维度身份，后续还得重做映射。

现在28个产品、56个规格均为开发资料，最多5条/产品，适合先做兼容设计和有限人工映射；等待正式目录、自由文本组合和外部引用积累后再改，迁移约束会更多。这是“现在值得进入设计”的判断，**不是允许立即迁移或证明外部集成已经可用**。

不推荐立刻上四张Option关系表：当前没有确认跨产品属性查询或共享属性字典，三维以内小矩阵可用产品JSON；只把需要稳定ID、唯一编码、独立查询的SKU落表，控制复杂度。若未来ERP规范明确要求共享属性，再按稳定ID迁移选项层。

## 3. 需要人工确认的决策

1. 是否采用B，以及是否接受“Options JSON+SKU表”的候选范围，而非立即建设通用商品中心。
2. Product Code与SKU Code的唯一范围、大小写规范、自动生成方式及人工改码权限；样例编码不作最终规则。
3. 参考价币种/精度，0/空值语义；inquiry模式是否隐藏所有SKU价；产品主价与SKU价如何同屏呈现。
4. simple/options/legacy模式、删除值默认停用且保留历史、全SKU停用时产品级咨询规则。
5. 候选3维/每维最多50值/当前组合最多50及退役历史保留；不是已批准业务参数。
6. 新旧客户端兼容期限、旧Admin写入阻断安排、人工映射负责人、原JSON归档位置/保留期与迁移批准门槛。

## 4. 建议实施阶段（未启动）

| 阶段 | 建议产出 | 进入下一步的门槛 |
|---|---|---|
| SKU-0 模型/DCR | 明确上述规则、契约、权限及文件白名单；独立批准数据库与媒体/咨询变化 | 人工批准目标模型与冻结例外 |
| SKU-1 服务与兼容基础 | 新表/迁移设计、事务校验、v1读取投影、旧写保护、媒体/咨询适配 | 隔离库契约/权限/回滚验证，先兼容后切换 |
| SKU-2 Admin | 简单模式、维度矩阵、稳定ID差分、MVP批量、legacy映射界面 | A/B/C/D场景和并发保存验证，遵守Admin Design System |
| SKU-3 游客增量接入 | 先保持原列表/详情读取，再支持按维选择、skuId咨询 | 旧包/新包、图片/价格/历史快照和真机回归 |
| SKU-4 数据迁移/人工映射 | 隔离dry-run、字段级对账、备份恢复演练、逐产品批准后切换 | 无损证据、人工映射确认；不得跳过兼容基础 |
| SKU-5 完整回归/人工验收 | 全后台、游客、权限、媒体、并发、历史与回退验证 | 人工验收；生产部署仍须另外授权 |

测试应贯穿各阶段，不能等SKU-5才第一次测迁移；Schema部署与实际数据切换须分开，旧客户端兼容完成前不启用破坏性模型。每个阶段是否独立Commit或同批交付由后续实施指令确定，本报告不自建实施任务。

本阶段仅完成规格/SKU模型审计，未修改业务代码、数据库、API、后台UI或游客端。等待人工确认后再进入实施设计。
